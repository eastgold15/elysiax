# 踩坑记录

elysiax 落地过程中遇到的非显然问题与最终解法，按主题分组。

## Bun 运行时与打包器

### 1. 运行时插件不拦截 bare / virtual 模块名

最初设计用 `virtual:modules` 虚拟模块聚合所有模块。实测：**Bun 运行时插件的 `onResolve` 只对路径形态的 specifier 生效**（`./`、`~/` 等），`virtual:modules`、bare 包名根本不会触发（用 `/.*/` filter 探针验证过）。

**解法**：落一个真实的 `src/modules.gen.ts` stub 文件（同时天然获得 TS 类型——ambient module 声明不支持相对路径），插件负责改写它的加载内容。

### 2. `Bun.Glob` 只匹配文件，不匹配目录

`new Glob("modules/*/")` 扫不到任何东西。要扫模块目录就直接匹配里面的文件：`modules/*/module.json`。

### 3. bunfig.toml 的 `preload` 必须放在文件顶部

TOML 的键值归属最近的 `[table]`。`preload` 写在 `[serve.static]` 之后就变成了那个表的键，静默失效。

### 4. `Bun.build` 不吃 bunfig 的运行时配置

`build.ts` 里两个坑：默认 browser 构建会拒绝 `import { serve } from "bun"`（要 `target: "bun"`）；bunfig 的 preload/static 插件对 `Bun.build` 不生效，必须手动传 `plugins: [tailwind, moduleAggregator()]`。

### 5. `bun build --compile` 的二进制里 preload 依然执行

编译产物中模块已在构建期内联，但 bunfig 的 `preload = ["./src/plugin.ts"]` 仍会跑，此时 `@elysiax/core/plugin` 无法解析。

**解法**：preload 改成 try/catch 动态 import，失败即静默（编译产物不需要运行时聚合）。

## Elysia 2.0

### 6. 破坏性变更清单（1.x → 2.0）

- 路由签名 `.post(path, handler, hook)` → `(path, hook, handler)`，旧顺序直接抛错
- `onError` → `error`、`onAfterResponse` → `afterResponse`、`resolve` 并入 `derive`
- scope 参数 `{ as: "scoped" }` → 字符串 `'plugin'`
- 类泛型变为 `Elysia<BasePath, Scope, Singleton, Definitions, Metadata, Routes, Ephemeral, Volatile>`

### 7. `derive` 不跨 `.use()` 兄弟插件边界

DI 插件挂到 app 上、模块 controller 再 `.use()` 上去时，controller 里拿不到 `di`。但 derive **沿同一实例链传播**。

**解法**：`elysiaxAPI()` 让 DI 插件实例自己去 `.use()` 各模块 controller，再整体挂进外层 app。模块代码的类型则由 `elysiaxModule<S>()` 门面补（框架内部一次断言，用户代码零 `any`）。

### 8. `@inferdi/elysia` 面向 Elysia 1.x，2.0 下直接崩

`withValidatedScope.onError is not a function`。

**解法**：把适配器复制到 `packages/elysia` 本地移植（API 改名 + 新泛型 + 结构化 RequestContext 替代 elysia 的 Context 导入），每请求 InferDI scope 得以保留。

## InferDI

### 9. 线性 builder 类型无法表达双向 Lazy 循环

`registerClass` 的 `deps` 只允许引用**已注册**的键。`userService ⇄ orderService` 互相依赖对方的 `*Lazy` 伴随键时，无论注册顺序如何，类型系统必然拒绝（运行时其实支持）。`Container<any>` 也不行——`NoKeyOverlap` 在 `keyof any` 下坍缩成 `never`。

**解法（架构层面）**：不做双向 Lazy。按限界上下文把依赖改单向（user → order），跨上下文组合上移到 controller——双向循环本质上是上下文边界没划清。

## TypeScript

### 10. `@kitajs/html/htmx` 的 types 指令在 TS7 下失效

tsconfig `types: ["@kitajs/html/htmx"]` 报 TS2688（子路径无法通过 `./*` 恒等通配导出解析，TS5.9 同样失败）。当前 app 不用 TSX 的 hx-* 属性，直接 `types: ["bun"]`。

## 桌面应用（webview-bun）

### 11. `Bun.WebView` 不是桌面窗口

Bun 1.4 的 `Bun.WebView` 是**无头浏览器**（自动化/测试/爬虫，类似 Puppeteer），macOS 用 WKWebView、其余平台走 CDP 驱动 Chrome——没有窗口概念。做窗口要用 `webview-bun`（Linux: WebKitGTK 6，Windows: 预装的 WebView2）。

### 12. `webview.run()` 是阻塞式 FFI 事件循环

与 Bun 的 HTTP server **同线程互斥**：同进程里 server 直接不响应。Worker 方案也不行——**Worker 里 bunfig preload 不生效，`plugin()` 注册也不拦截 worker 的模块解析**（模块列表为空，全部 404）。

**解法**：server 放独立子进程。开发时 spawn `bun src/index.ts`；编译后 spawn 自身加 `--server` 参数，入口按 argv 分流（漏了这个分支会导致无限自 spawn 卡死）。窗口关闭后 `server.kill()`。

### 13. makepkg 的 strip 会毁掉 bun compile 二进制

症状：安装后运行只打印 Bun 帮助文本——strip / debug 分离把二进制尾部的内嵌负载剥掉了。

**解法**：PKGBUILD 加 `options=('!strip' '!debug')`。

### 14. 各平台窗口依赖

- Linux：`webkitgtk-6.0` + `gtk4`（PKGBUILD 已声明 depends）
- Windows：WebView2（Win10/11 预装），交叉编译 `compile: { target: "bun-windows-x64", windowsIcon, windowsHideConsole: true }`
- 窗口图标在 Linux 上不来自进程，而来自 `.desktop` 文件 + hicolor 图标，打包时安装到 `/usr/share/icons/hicolor/256x256/apps/`

## .elysiax/ 代码生成（.next 模式）

### 15. 虚拟插件不如真实生成文件

旧的 `moduleAggregator` Bun 插件 + `modules.gen.ts` stub 方案在四个场景下各踩一次坑（见 #1/#4/#5/#12）：运行时解析、`Bun.build`、`--compile` 二进制、Worker。改成 **codegen 生成真实文件到 `.elysiax/`**（类似 `.next/`）后这些坑全部消失——生成物是普通 TS，所有工具链天然兼容。装配顺序（拓扑排序）与 lazyKey 伴随键也由生成器从依赖声明推导，不再手写。

### 16. `bunx elysiax dev` 跑起来的"应用"是系统里安装的桌面程序

排查 log 与代码对不上时发现：`bunx` 在本地 `node_modules/.bin` 找不到 `elysiax` 就回退到 PATH，命中了之前 `pacman` 安装的 `/usr/bin/elysiax`（桌面二进制，忽略 argv 直接起服务）。**workspace 包的 bin 只有在被某个包依赖时才会链接**——app 需要把 `@elysiax/cli` 加进自己的 devDependencies。这也是一个教训：系统里装过同名命令后要警惕 PATH 遮蔽。

### 17. cerebro 的 execute 返回即退出，后台 watcher 全灭

CLI 的 `dev` 命令里 spawn 了 `bun --hot` 子进程并注册了 `setInterval` watcher，但 `execute()` 一返回 cerebro 就退出进程，watcher 死掉、只剩孤儿 server。症状：文件改了不重新生成。

**解法**：`await new Promise(r => child.on("exit", r))` 把 execute 挂到子进程生命周期上。

### 18. typecheck 依赖代码生成的产出

`.elysiax/` 不入库，clone 后直接 `tsc` 会因找不到 `../.elysiax` 报错。各 app 的 typecheck 脚本改为 `elysiax gen && tsc --noEmit`（turbo 任务图里先生成再检查）。

### 19. webview-bun 发布的是 .ts 源，skipLibCheck 管不到

它的 `Pointer` 类型与当前 bun-types 不兼容（TS2322），而 `skipLibCheck` 只跳过 `.d.ts`。用 tsconfig `paths` 把 `webview-bun` 映射到本地最小声明文件解决（`src/types/webview-bun.d.ts`）。

### 20. PNG 可以直接包进 ICO，不需要图像工具

Windows 图标需要 `.ico`，但 Vista 起 ICO 支持 PNG 载荷——写一个 22 字节的 ICONDIR/ICONDIRENTRY 头再接 PNG 原始数据即可（宽高从 IHDR 第 16-24 字节读）。CLI 的 Windows 交叉编译因此零外部依赖（不需要 ImageMagick/rsvg）。

### 21. Bun isolated install：workspace 链接不在根 node_modules

Bun 的 isolated 模式把 `@elysiax/*` 的 workspace 符号链接放在**各包的** node_modules 里，根 node_modules 没有。在 monorepo 外测试模板项目时，软链根 node_modules 会找不到 workspace 包，要链到某个 app 的 node_modules。

## Dockyard（部署工具）

### 22. elysia 惰性加载 typebox 是**运行时** require，`bun --compile` 后必死

Elysia 2.x 的 `dist/type/typebox-type.mjs` 不用静态 import，而是首次用时 `import.meta.require ?? createRequire(...)` 执行 `req("typebox/type")`。bundler 无法静态分析这种调用，`bun build --compile` 不会把 typebox 打进去——dev 正常（node_modules 可解析），编译产物在**第一次编译带 schema 的路由**时就抛 `Cannot find module 'typebox/type' from '/$bunfs/...'`；若 controller 在模块顶层调 `t.Numeric()` 等 stub，启动即死。

**解法**（已收进 `@elysiax/core` 的 `start.ts` 模块顶层）：用 elysia 官方逃生口 `setupTypebox` 静态注入，import 会被打进产物、注入后跳过运行时解析：

```ts
import { setupTypebox } from "elysia";
import * as typeboxType from "typebox/type";
import * as typeboxSystem from "typebox/system";
import * as typeboxValue from "typebox/value";
import * as typeboxSchema from "typebox/schema";
import * as typeboxCompile from "typebox/compile";

setupTypebox({ typebox: { type: typeboxType, system: typeboxSystem, value: typeboxValue, schema: typeboxSchema, compile: typeboxCompile } });
```

三个要点：① 必须在**模块顶层**执行——controller 模块 import 阶段就会触发 stub，放进 `start()` 函数体里太晚；② 谁创建 Elysia 实例谁注入（monorepo 下 elysia 有多个 peer 哈希副本，app 侧注入可能到不了 core 用的那份；不过 bun 打包时会去重成一份）；③ 包裹 `typebox` 必须是直接依赖。调试技巧：给 `resolveNamespaces` 打 `console.trace` 重编译，能看到是谁在 import 阶段触发的加载。

### 23. `gh api` 遇到 304 会以非零码退出

用 `If-None-Match` 做 ETag 轮询时，命中 304 的响应没有 body，`gh api` 解析 JSON 失败报 `unexpected end of JSON input` 并以非零码退出——但响应头（含 `304`）已打印到 stdout。

**解法**：先检查 stdout 首行是否含 `304`（是则视为"无变化"），再判断退出码报错。

### 24. drizzle-orm@rc 的两个 API 变化

- sqlite config **不再接受 `schema`**（`Omit<DrizzleConfig, 'schema'>`）——没有 `db.query.*`，统一用 `db.select()/insert()/update()/delete()` 核心 API
- 列名默认 **camelCase**（`projectId` 而非 `project_id`）——手写 SQL 迁移会和 schema 对不上，迁移 SQL 必须以 `drizzle-kit generate` 输出为准
- `bun --compile` 后没有文件系统里的 migrationsFolder：用 `migrate(db, journalArray)` 变体（`{ sql, timestamp, name }[]`），把迁移日志内嵌成纯 TS 模块

### 25. dockerode `container.exec` 的两个挂死点

在容器里跑管理命令（如 `psql` 建库）时：

1. **不能开 `Tty: true`**——psql/mysql 等 CLI 检测到 TTY 会起 pager（less），exec 永远等用户按 q，流不结束。不开 Tty 输出是多路复用的，要用 `docker.modem.demuxStream(stream, stdout, stderr)` 拆流
2. **`exec.start()` 要传 `{ hijack: true, stdin: false }`**——不传 hijack 时经自定义传输（如 SSH 中继 socket）可能拿不到响应流

另外 postgres 侧：`CREATE DATABASE` 不能与其他语句同处一个隐式事务（单个 `-c` 多语句会包事务），`CREATE USER` 和 `CREATE DATABASE` 必须分两次 exec；上次失败留下的孤儿 role 用 `DROP USER IF EXISTS` 前缀兜底。
