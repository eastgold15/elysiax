# Dockyard 界面设计规范

> 状态：设计方向已由用户确认，以下尺寸与模式作为后续实施基线；尚未完成样板页视觉验收。
> 建立日期：2026-10-25。页面实施与验收状态见 [页面进度表](../docs/design/pages.md)。本文件是视觉契约，不是“已实现”的声明。

## 1. 方向与边界

**克制的开发者工具**：低饱和深色背景、细边框、清晰排版、适度紧凑。让项目、服务器、部署状态与下一步操作先被看见，而不是装饰。

- **使用者与任务**：熟悉开发工具的人，在本地项目、远端服务器和部署日志之间切换；快速找到异常、判断归属、配置依赖、执行部署并确认结果。
- **领域**：仓库、服务器、船台、部署流水线、容器、依赖连线、运行日志、主机信任、共享资源。
- **色彩来源**：港湾近黑、船体蓝灰、钢板灰、仪表浅灰、黄铜操作件、潮水青绿、故障信号红。沿用现有 Harbor / Brass / Tide / Signal，不另起配色。
- **产品标识性**：项目 → 服务器 → 分组 → 应用 → 服务的归属结构；列表中用名称、地址、状态和操作表达，画布中用嵌套容器与依赖线表达。部署动作始终能追到日志与结果。
- **拒绝的默认方案**：大面积彩色渐变 → 安静的 Harbor 表面；首页堆满统计卡片 → 以项目和任务列表为中心；每页独立装饰主题 → 同一套控件与状态语言。
- **参考方向**：借鉴开发者工具的层级、密度和克制，不照搬某个产品的布局；本轮没有选择图片参考、没有生成视觉样板。

### 范围

适用于 projects、servers、canvas、弹窗、抽屉及其加载/错误/空态。画布可以改变布局模型，不能另起字体、配色或控件体系。

htmx 与 Solid **共享视觉契约，不共享运行时**：htmx 页面用服务端模板；canvas 是整页 Solid client，壳由 HTMLBundle 服务。不得让两个渲染器操作同一 DOM，不得为复用视觉引入 React 或让 client 导入服务端值级代码。

## 3. 颜色与层级

### 现有颜色原语

| 原语 | 当前值 | 约定角色 |
|---|---|---|
| Harbor 950 | `#0b0f14` | 页面/画布底层、内凹输入区与日志区 |
| Harbor 900 | `#11161d` | 内容表面、面板、列表悬停背景 |
| Harbor 800 | `#1a222c` | 浮层/菜单目标表面、轻量分隔、选中项底色 |
| Harbor 700 | `#243040` | 标准边框、输入框边框 |
| Harbor 600 | `#33445a` | 强调边界，不作全页默认边框 |
| Brass 500 | `#d9a441` | 主操作、当前选择/焦点、依赖关系、警告 |
| Brass 600 | `#b98a2f` | 主按钮悬停 |
| Tide 400 | `#5ec4b6` | 成功、运行中、就绪 |
| Signal 500 | `#d95d4e` | 失败、危险、破坏性操作 |

Brass 的操作与警告角色用形态区分：主操作为实底按钮；警告为文字/图标加淡底提示，不把整片内容涂黄。Tide 不作为第二主操作色。依赖线使用 Brass 虚线并配箭头，不靠颜色独自表达方向。

### 表面、文字与边框

- **深度策略**：以细边框分层为主，辅以同色系轻微明度变化。普通列表/卡片不用大阴影；浮层允许一套轻量遮挡阴影，不与厚重投影混用。现有 `shadow-xl/2xl` 是待收敛项，不是新规范。
- 导航与主工作区属于同一个 Harbor 世界，不再一边 neutral、一边 Harbor。导航通过分隔与选中状态辨识，不新增醒目的彩色侧栏。
- 浮层应比承载它的表面高一级；输入区在面板内显得内凹。避免大面积透明叠色使层级失控。
- 文字四级：主信息 `neutral-100`；正文 `neutral-300`；辅助说明 `neutral-400`；非关键元数据 `neutral-500`。`neutral-600` 不用于必读内容、错误原因和可操作控件标签。禁用不能只靠改成低对比文字。
- 分隔可用 `harbor-800/60`；标准控件边框用 `harbor-700`；选中/键盘焦点用 Brass。不要让每个嵌套区域都有强边框。
- 对比度需在实际背景上验收：普通文字目标至少 4.5:1，大字及必要的控件边界/状态指示目标至少 3:1。颜色归一不等于已通过对比度检查。
- 本轮固定深色基线，不顺带承诺浅色主题已完成。

## 4. 排版、密度与空间

### 字体

沿用现有 `font-sans`，不增加字体下载依赖；中文优先可读性与系统回退。路径、主机、端口、服务名、日志、环境变量使用现有 `.mono` / `ui-monospace` 字体栈。不要整页全部等宽。动态计数与数值列使用 `tabular-nums`。

| 层级 | 目标字号 / 行高 / 字重 | 用法 |
|---|---|---|
| 页面标题 | 20 / 28px / 600 | projects、servers 主标题 |
| 面板标题 | 16 / 24px / 600 | 抽屉、弹窗、主要分区 |
| 正文与控件 | 14 / 20px / 400–500 | 表单、列表、按钮 |
| 辅助信息 | 12 / 16px / 400 | 路径、描述、字段提示 |
| 紧凑标记 | 11 / 16px / 500 | 非交互 badge、画布元数据；不承载关键指令 |

尺度以约 1.2 的层级关系为参考，按原生字号取整；用字重、颜色和留白共同分层，不只是放大文字。画布工作条标题可保留 14 / 20px / 600，避免抢夺节点工作区的注意力。

### 空间与尺寸基线

- 空间基准 **4px**：常用间距 4 / 8 / 12 / 16 / 24 / 32px；边框 1px、光学对齐属于明确例外。
- 页面水平内边距 24px；窄屏 16px。相关控件间距 8px；表单项间距 12–16px；分区间距 24px。
- 标准面板内边距 16px；抽屉/弹窗 20px；不要每个面板自选 13/17/23px。
- 标准控件高 36px；密集工具区视觉高 32px；触控场景采用至少 44px 命中区。桌面紧凑控件仍需足够间隔，不能把 44px 描述成所有 WCAG 等级统一的硬性要求。
- 列表行默认最小高 48px；长路径或操作换行时允许增高，不能固定高度裁字。
- 圆角：控件/徽章 4px，内容卡片 6px，弹窗 8px；抽屉贴边处不加外侧圆角。画布嵌套卡片避免每层同样大的圆角。

这些是目标值，不宣称旧组件已统一；偏差记录在进度表中，避免为了追数字临时覆盖大量内联类名。

## 5. 组件契约

| 模式 | 目标规格与行为 |
|---|---|
| 主按钮 | 36px 高，水平 12px，4px 圆角，14px/600；Brass 实底 + Harbor 950 文字；同一操作组只突出一个主要任务 |
| 次按钮 | 与主按钮同高，Harbor 边框/表面；用于取消、配置等次要动作，不另造一组强调色 |
| 紧凑按钮 | 32px 视觉高，水平 8px，12px/500；仅用于列表/画布工具区，不能缩成难以点击的文字碎片 |
| 危险操作 | Signal 文字或弱底；执行中/执行前说明影响范围。删除记录、删除远端资源与删除本地文件必须在文案中区分 |
| 输入/选择 | 默认 36px 高，水平 12px，4px 圆角；Harbor 950 内凹底，Harbor 700 边框；永久标签，placeholder 不替代标签 |
| 键盘焦点 | 明显的 Brass 外环/outline 与偏移；不能只有 `outline-none`。错误时保留焦点识别，不只换红边框 |
| 状态徽章 | 11px/500，水平 6px、垂直 2px；淡底 + 文字；运行中/排队/失败/未检测等必须有文本，状态点只是辅助 |
| 列表行 | 名称最先被识别，主机/路径其次，状态与操作对齐；不要把每一行都包装成浮起的大卡片 |
| 日志/终端 | 等宽字体、独立滚动，保留错误与时间信息；复制结果给反馈，敏感字段不能为截图或提示直接暴露 |
| 空态 | 说明“为什么为空”与一个可执行的下一步；错误/无权限不是“没有数据” |

### 页面结构

- 列表页：导航 → 标题与数量 → 主操作 → 主体列表；不加与任务无关的欢迎横幅/统计墙。
- 导航：延续现有约 208px 宽的桌面导航基线；当前项有 `aria-current` 等可识别状态；窄屏有可访问的折叠入口，不让侧栏挤没主体。
- 页头：目标最小高 64px，24px 水平内边距；窄屏可换行。canvas 工作条可保留现有 56px 的紧凑布局，两者共享控件和文字颜色。
- 页面以名称、状态、下一步动作为焦点。一个视图不能同时让巨大标题、彩色状态卡和多个主按钮争抢注意力。

### 弹窗、抽屉、菜单

- 小弹窗目标宽 384px；普通表单约 480px；宽内容约 672px；均须保留至少 16px 视口边距，内容高不超过约 85vh，溢出内部滚动。
- 默认右侧抽屉宽 576px，宽抽屉上限约 768px；窄屏全宽。避免只写 `50vw` 导致内容在不同屏幕上过窄或过宽。
- 页头与关闭入口保持可用，正文独立滚动；背景遮罩统一约黑色 60%，不混用多档强模糊。
- 必须具备语义标题、可访问关闭名称、Escape、焦点进入/约束/返回、背景不可交互。优先原生 HTML 与已有成熟组件；不要自行重写不完整的弹层行为。
- **Solid client（canvas）的弹层基座定为 `@kobalte/core`**（2026-10-26 用户确认）：无头组件自带焦点约束/Esc/aria，样式全部走本规范的 Tailwind 色板；toast/确认框/输入框统一走 `client/feedback.tsx`（`toast()`/`confirmAction()`/`promptAction()`），禁止再出现原生 `alert/confirm/prompt`。
- **两渲染器同一副面孔**（2026-10-26 用户确认）：Kobalte 是无头库、本身无视觉风格，"风格"= 本规范的色板与尺寸规格——htmx 侧弹层（shared/ui、shadcn-htmx 组件）必须按 canvas Kobalte 弹层的同一规格实现，行为层用原生 `<dialog>` 拿 Esc/焦点语义，不引 JS 弹层库。验收时同规格双侧对照，不允许各写一套。
- 菜单在视口内定位，支持键盘导航、Escape、点击外部关闭；右键入口不能是关键操作唯一入口。
- 层级按底层内容 → 菜单 → 模态遮罩/面板 → toast 排序；canvas client 落为：菜单 `z-50` < 模态 `z-[60]` < toast `z-[70]`（Kobalte Portal 渲染）。

### 全状态与动效

- 控件需 default / hover / active / focus-visible / disabled；数据区需 loading / empty / error / success。异步提交显示“正在做什么”、防重复提交，失败保留已填数据并可重试。
- 可恢复错误优先字段或操作区内联；成功可用轻量 toast。主机信任与危险删除保留明确确认，不为了简约删掉安全步骤。
- 短交互 120–160ms，菜单 150–200ms，抽屉 180–240ms；位移动效只用 transform/opacity，禁止 `transition: all`。高频画布拖拽不加延迟缓动；尊重 `prefers-reduced-motion`。
- 小屏不隐藏唯一操作。长仓库名/路径可以截断，但能查看或复制全文；终端/表格可局部横向滚动。

## 6. 画布例外：自由布局，不另起风格

- 保留服务器 → 分组 → 应用 → 服务的嵌套归属、数据库依赖线和状态订阅；几何数据由业务布局模型管理，不用全局排版网格强行改写已保存坐标。
- 24px 基准点阵只辅助定位，不与内容争抢。依赖线为 Brass 虚线 + 方向箭头；连接点有可辨识命中区域与说明。
- 节点标题、徽章、按钮、抽屉必须与列表页采用同样语义；颜色不能代替名称、图标或状态文字。
- 现有节点尺寸、服务卡间距与布局常量相互关联；改节点排版时同步检查 `board.tsx` 的估算尺寸，避免遮挡按钮/子节点。不直接把设计文档中的普通行高套到画布全部几何。
- 不因追求美观改变依赖关系、部署确认、拖拽持久化等业务行为。拖动、缩放、连接、缩放后点击、键盘和窄屏需要独立验收。

## 7. 复用与禁止事项

- htmx 先用 `src/shared/ui/` 与 `snippets/`；Solid 先看本原子内已有实现。组件外观一致不意味着必须跨原子引入隐式共享运行时。
- 可复用模式至少有两处真实用途再抽取；跨原子分发仍遵守 socket 与显式依赖，不为 DRY 破坏原子完整性。
- 不新增没有任务含义的色彩、渐变、重投影、巨型圆角、emoji 装饰。已有 emoji 暂不批量替换，先选定统一图标来源与可访问标签。
- 不为新页面另挑字体、按钮尺寸、面板阴影或交互反馈。确需例外时，先在本文件写原因和范围。
- 不将 shadcn 默认配色整套覆盖 Harbor；不复制仅适配 React 的行为组件到 Solid/htmx。
- 不把“文档已写”“源码已改”“浏览器验证通过”“用户确认”混为一个完成状态。

## 8. 后续工作与验收

1. 每次 UI 任务先读本文件，再读页面进度表及受影响源码；以仓库产物恢复设计，不依赖上一轮聊天。
2. 当前首个样板候选为 **servers 列表 + 添加表单 + 状态/信任反馈**：覆盖通用控件且业务范围明确。先实施这一条，不并行重画整个应用。
3. 实施前简述该视图的任务焦点、颜色/层级和复用入口；如果变更核心方向，先请用户确认。
4. 运行项目、构建、测试、浏览器检查前，遵守 `CLAUDE.md` 的“进行测试需要询问用户”。没有批准就保持待验证状态。
5. 验收至少覆盖桌面/窄屏、长文本、多数据、空态、加载、失败、键盘焦点、弹层以及状态对比；记录实际视口、检查日期和证据路径，不能编造截图或通过结论。
6. 样板页由用户确认后，在进度表登记其版本/证据，再扩展到 projects、canvas 与抽屉；没有确认不把目标尺寸描述成已验收模式。
7. 新模式或有意偏差需同步更新本文件与进度表；保留确认来源与剩余问题。规范更新与实现同一批审查，不静默重写全应用风格。
